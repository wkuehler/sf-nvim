1. INTRODUCTION                                         *sf-nvim-introduction*

sf-nvim wraps the Salesforce CLI (`sf`) so common SFDX tasks can be run from
inside Neovim: Apex tests with failures in the quickfix list, deploy/retrieve,
org and scratch org management, and anonymous Apex execution.

Long-running commands (tests, deploys, scratch org creation) run in a terminal
split at the bottom of the screen (see |sf-nvim-terminal|). The split stays
open until you press <Enter> or `q`, so the full CLI output is always
visible. Quick lookups — the org
picker behind |:Sf-config-org|, `sf config set`, |:Sf-org-open| — run in the
background with |vim.system()| and report through |vim.notify()|. User
feedback goes through |vim.notify()|, |vim.ui.select()| and |vim.ui.input()|,
so the plugin picks up whatever UI overrides you already use.

==============================================================================
2. REQUIREMENTS                                         *sf-nvim-requirements*

- Neovim 0.10 or later (uses |vim.system()|)
- Salesforce CLI (`sf`) on $PATH and authenticated to at least one org
- ripgrep (`rg`) on $PATH, used to find Apex class files for quickfix
- An SFDX project. The plugin treats the current working directory (see
  |getcwd()|) as the project root; start Neovim from the directory that
  contains `sfdx-project.json`.

Run `:checkhealth sf-nvim` to confirm. See |sf-nvim-health|.

3. SETUP                                                       *sf-nvim-setup*

Nothing is registered until |sf-nvim.setup()| is called: >lua

    require("sf-nvim").setup({
        enable_default_keybinds = true,
    })
<
With lazy.nvim: >lua

    { "wkuehler/sf-nvim", opts = { enable_default_keybinds = true } }
<

4. CONFIGURATION                                              *sf-nvim-config*

All options with their defaults: >lua

    require("sf-nvim").setup({
        test_results_dir = "test-results",
        auto_open_quickfix = true,
        test_wait_time = 15,
        enable_default_keybinds = false,
        leader_prefix = "<leader>s",
        deploy_on_save = false,
        tail_notify = true,
    })
<
                                              *sf-nvim-config.test_results_dir*
test_results_dir        (string, default `"test-results"`)
        Directory, relative to the project root, where the JSON output of
        each test run is saved as `<Class>_<timestamp>.json` (or
        `all-tests_<timestamp>.json`). Add it to `.gitignore`.

                                            *sf-nvim-config.auto_open_quickfix*
auto_open_quickfix      (boolean, default `true`)
        Open the quickfix window automatically when a test run produced
        failures.

                                                *sf-nvim-config.test_wait_time*
test_wait_time          (integer, default `15`)
        Minutes passed to `sf apex run test -w`. The CLI polls for that long
        before giving up on a run.

                                       *sf-nvim-config.enable_default_keybinds*
enable_default_keybinds (boolean, default `false`)
        Install the keymaps listed in |sf-nvim-keymaps|.

                                                 *sf-nvim-config.leader_prefix*
leader_prefix           (string, default `"<leader>s"`)
        Prefix for the default keymaps.

                                                *sf-nvim-config.deploy_on_save*
deploy_on_save          (boolean, default `false`)
        On |BufWritePost| of any file under one of the project's package
        directories (from `sfdx-project.json`), run |:Sf-project-file| for
        it. Failures are reported through quickfix like a manual deploy.

==============================================================================
5. COMMANDS                                                 *sf-nvim-commands*

                                                                         *:Sf*
:[range]Sf {group} {action}
        Single entry point for every action. Both arguments tab-complete.
        A [range] is passed to the action; only |:Sf-apex-selection| uses it.

Test group ~
                                                            *:Sf-test-current*
:Sf test current
        Run the tests in the Apex class in the current buffer (the file must
        have a `.cls` extension). When the run finishes, failures are loaded
        into quickfix. See |sf-nvim-quickfix|.

                                                             *:Sf-test-method*
:Sf test method
        Run only the test method under the cursor (`--tests Class.method`).
        The method is found by walking upward to the nearest `void name(`
        declaration that is marked `@IsTest` (on its annotation lines) or
        `testMethod`; `@TestSetup` and plain helpers are rejected.

                                                                *:Sf-test-all*
:Sf test all
        Run every test in the org, same result handling as above.

                                                               *:Sf-test-load*
:Sf test load
        Load the most recent saved result file from
        |sf-nvim-config.test_results_dir| into quickfix and open it.

                                                              *:Sf-test-clear*
:Sf test clear
        Delete all saved result files, after confirmation.

Apex group ~
                                                            *:Sf-apex-execute*
:Sf apex execute
        Run the current file as anonymous Apex (`sf apex run -f {file}`).

                                                          *:Sf-apex-selection*
:{range}Sf apex selection
        Run the lines in {range} as anonymous Apex. Without a range, the last
        visual selection (`'<`,`'>`) is used. The lines are written to a
        temporary `.apex` file which is deleted after the run.

                                                   *sf-nvim-config.tail_notify*
tail_notify             (boolean, default `true`)
        Show a |vim.notify()| message for each debug log captured by
        |:Sf-log-tail|. The counter in |sf-nvim.status()| updates either way.

                                                              *:Sf-apex-debug*
:Sf apex debug
        Run the current file as anonymous Apex in the background
        (`sf apex run -f {file} --json`) and open the result in the
        `sf://apex-run` buffer. See |sf-nvim-logs|.

                                                     *:Sf-apex-debugselection*
:{range}Sf apex debugselection
        Same as |:Sf-apex-debug| for the lines in {range} (default: the last
        visual selection).

Log group ~
                                                                *:Sf-log-list*
:Sf log list
        `sf apex list log --json` into a picker; the chosen log opens in
        `sf://log/{id}`. See |sf-nvim-logs|.

                                                              *:Sf-log-latest*
:Sf log latest
        Open the most recent stored log (`sf apex get log --number 1`) in
        `sf://log/latest`.

                                                                *:Sf-log-tail*
:Sf log tail
        Toggle a background `sf apex tail log`. No window is opened: output
        accumulates in the hidden `sf://log/tail` buffer (last 5000 lines),
        each new log increments the counter shown by |sf-nvim.status()| and,
        with |sf-nvim-config.tail_notify|, posts a notification. Creates a
        trace flag for the running user if none is active. Run again to
        stop. An unexpected exit (expired token, etc.) is reported as an
        error. The process is killed on |VimLeavePre|.

                                                                *:Sf-log-show*
:Sf log show
        Open `sf://log/tail` in a split with the cursor at the end, so new
        output is followed while the window is open; move the cursor up to
        stop following, `G` to resume. `q` closes the window; the tail
        keeps running.

SOQL group ~
                                                              *:Sf-soql-buffer*
:Sf soql buffer
        Run the whole buffer as a SOQL query. See |sf-nvim-soql|.

                                                           *:Sf-soql-selection*
:{range}Sf soql selection
        Run the lines in {range} (default: the last visual selection).

                                                              *:Sf-soql-prompt*
:Sf soql prompt
        Ask for a query with |vim.ui.input()| and run it.

Org group ~
                                                                *:Sf-org-open*
:Sf org open
        `sf org open` in the background; the org URL (or the error) is
        shown with |vim.notify()|.
                                                                *:Sf-org-list*
:Sf org list            `sf org list`
                                                                *:Sf-org-info*
:Sf org info            `sf org display`
                                                              *:Sf-org-create*
:Sf org create
        Create a scratch org. Prompts, in order, for a definition file
        (every `config/**/*-scratch-def.json` in the project), duration in
        days (default 7), and an alias; then runs
        `sf org create scratch --definition-file ... --duration-days ... --alias ...`.

Config group ~
                                                              *:Sf-config-org*
:Sf config org
        Pick from the authenticated orgs and set it as `target-org`
        (`sf config set target-org`). The org list is fetched in the
        background; the picker opens when it arrives.

                                                              *:Sf-config-hub*
:Sf config hub
        Pick from the authenticated Dev Hubs and set `target-dev-hub`.

Project group ~
                                                            *:Sf-project-file*
:Sf project file
        Deploy the current buffer's file in the background with
        `sf project deploy start --source-dir {path} --json`. {path} is the
        LWC or Aura bundle directory when the file is inside one, the
        described file when the buffer is a `-meta.xml` companion, and the
        file itself otherwise. The file must be under a package directory
        listed in `sfdx-project.json`. Success is reported with
        |vim.notify()|; failures fill quickfix (see |sf-nvim-deploy-quickfix|).

                                                           *:Sf-project-fetch*
:Sf project fetch
        Retrieve the current file (or bundle) from the org with
        `sf project retrieve start --source-dir {path}`, then |:checktime|.

                                                          *:Sf-project-deploy*
:Sf project deploy
        `sf project deploy start` in a terminal split. If it exits non-zero,
        `sf project deploy report --json` is fetched and any failed
        components are loaded into quickfix.
                                                        *:Sf-project-retrieve*
:Sf project retrieve    `sf project retrieve start`
                                                        *:Sf-project-validate*
:Sf project validate
        `sf project deploy start --dry-run`, with the same quickfix
        handling as |:Sf-project-deploy|.

6. KEYMAPS                                                   *sf-nvim-keymaps*

Installed only when |sf-nvim-config.enable_default_keybinds| is true. Shown
with the default prefix `<leader>s`. Keys are grouped by a prefix letter:
`t` tests, `a` anonymous Apex, `l` debug logs, `q` SOQL, `o` org, `c` config,
`p` project. When which-key.nvim is installed the groups are labelled from
`require("sf-nvim").groups` (a `name -> {prefix, label}` table).

    <leader>stc     :Sf test current
    <leader>stm     :Sf test method
    <leader>sta     :Sf test all
    <leader>stl     :Sf test load
    <leader>stx     :Sf test clear
    <leader>sae     :Sf apex execute            (normal mode)
    <leader>sae     :Sf apex selection          (visual mode)
    <leader>sad     :Sf apex debug              (normal mode)
    <leader>sad     :Sf apex debugselection     (visual mode)
    <leader>sll     :Sf log list
    <leader>slL     :Sf log latest
    <leader>slt     :Sf log tail
    <leader>sls     :Sf log show
    <leader>sqb     :Sf soql buffer
    <leader>sqq     :Sf soql prompt
    <leader>sq      :Sf soql selection          (visual mode)
    <leader>soo     :Sf org open
    <leader>sol     :Sf org list
    <leader>soi     :Sf org info
    <leader>soc     :Sf org create
    <leader>sco     :Sf config org
    <leader>sch     :Sf config hub
    <leader>spf     :Sf project file
    <leader>spF     :Sf project fetch
    <leader>spd     :Sf project deploy
    <leader>spr     :Sf project retrieve
    <leader>spv     :Sf project validate

To define your own, leave the option off and map to |:Sf| or to the functions
in `require("sf-nvim").actions` (see |sf-nvim-api|).

7. TEST RESULTS AND QUICKFIX                                *sf-nvim-quickfix*

A test run invokes `sf apex run test` twice: once with `--json`, redirected to
a timestamped file in |sf-nvim-config.test_results_dir|, and once plain so the
terminal split shows readable progress. When the split closes the JSON file is
parsed; every test whose outcome is `Fail` or `CompileFail` becomes a quickfix
entry with:

- the class file, located with `rg --files --glob '**/<Class>.cls'`
- line and column, taken from the first `line N, column M` in the stack trace
- the failure message

A summary is shown with |vim.notify()|. Failures whose class file could not be
found are counted in that summary rather than dropped. Use |:cnext| and
|:cprevious| to move between failures.

                                                     *sf-nvim-deploy-quickfix*
Deploy failures ~

`sf project deploy ... --json` lists every component in `result.files[]`.
Entries with `state == "Failed"` become quickfix entries (title
"Deploy failures") using their absolute `filePath`, `lineNumber`,
`columnNumber`, and `error`; components without a location (e.g. a custom
field) point at line 1 of their metadata file. The quickfix window opens
automatically when |sf-nvim-config.auto_open_quickfix| is set.

8. THE TERMINAL SPLIT                                       *sf-nvim-terminal*

Commands run through `runner.term` open a |:terminal| in a bottom split. The
split is left in Normal mode with the cursor on the last line, which makes
Neovim follow new output as it arrives (see |terminal-input|) while every
ordinary motion still works — <C-u>, <C-b>, `k`, `gg`, `?pattern` — so you
can scroll back through long output at any time. Moving the cursor off the
last line stops the following; `G` resumes it.

When the command finishes the split shows: >

    [sf-nvim] Done. Press ENTER or q to close.
<
Buffer-local mappings in that split:

    <CR>  (Normal)      close the split (answers the prompt)
    q     (Normal)      same
    <Esc> (Terminal)    back to Normal mode, if you entered Terminal mode
                        with `i` to type at the command

Pressing <CR> or `q` while the command is still running does nothing
harmful — the keystroke goes to the command's stdin — but the split stays
open until the command exits. The buffer is wiped when the split closes.

9. DEBUG LOGS                                                   *sf-nvim-logs*

Logs open in read-only scratch buffers (|sf-nvim-scratch|) with
'filetype' `apexlog`; the plugin ships a small syntax file that highlights
timestamps, event names, `USER_DEBUG` lines, exceptions, SOQL/DML events
and limit usage.

|:Sf-apex-debug| runs anonymous Apex with `--json`, so the log comes back
inline and no stored log is needed. The `sf://apex-run` buffer starts with
a verdict line: >

    == Anonymous Apex: success
    == Compile error at line 1, column 13
    Unexpected token '('.
    == Runtime exception: System.MathException: Divide by 0
       AnonymousBlock: line 1, column 1
<
followed by a blank line and the full log. The same verdict is shown with
|vim.notify()|.

|:Sf-log-list| and |:Sf-log-latest| read logs stored in the org, which only
exist while a trace flag is active for the running user. The quickest way
to get one is |:Sf-log-tail|, which creates the flag and streams logs;
Setup > Debug Logs works too. With no stored logs both commands warn
"No stored debug logs. :Sf log tail creates a trace flag." rather than
opening an empty buffer.

10. SOQL                                                        *sf-nvim-soql*

Queries run with `sf data query --query {q} --json` against the target org.
Before running, buffer lines are joined into one query: lines starting with
`//` or `--` are dropped, whitespace is collapsed, and a trailing `;` is
removed.

Results render in the `sf://query` scratch buffer ('filetype' `soqlresult`): >

    -- SELECT Id, Name, Owner.Name, (SELECT Id FROM Contacts) FROM Account
    -- 2 of 2 row(s)
    Id                  Name       Owner.Name         Contacts
    ------------------  ---------  -----------------  --------
    001000000000000AAA  Account 0  Automated Process
    001000000000001AAA  Account 1                     [2 rows]
<
- Columns follow the order of the SELECT clause; anything the API returned
  that was not named there (aggregate `expr0` etc.) is appended
  alphabetically.
- Relationship fields are flattened with dots (`Owner.Name`).
- Child subqueries are summarised as `[N rows]`.
- `null` renders as an empty cell.
- When the result is truncated (`done == false`) the count line says
  "(more available)"; add a LIMIT or narrow the query.

A failed query shows the CLI's error — including its caret line pointing at
the offending column — in the same buffer, and the last line of the message
with |vim.notify()|.

11. FILETYPES                                              *sf-nvim-filetypes*

`ftdetect/sf-nvim.lua` registers with |vim.filetype.add()|:

    .soql               soql
    .apex               apex
    .apexlog            apexlog
    .cls, .trigger      apex — only when an `sfdx-project.json` exists in a
                        parent directory, so other languages' `.cls` files
                        are not affected

Only `apexlog` ships with syntax highlighting. For `apex` and `soql`, use
your preferred syntax plugin or Tree-sitter grammar.

                                                             *sf-nvim-scratch*
Scratch buffers ~

`sf://apex-run`, `sf://log/{id}`, `sf://log/latest` and `sf://query` are
'buftype' `nofile`, read-only, and reused by name: running the same action
again replaces the contents and focuses the existing window instead of
opening another split. `q` closes the window; the buffer is kept hidden and
can be reopened with |:buffer|.

12. LUA API                                                      *sf-nvim-api*

                                                             *sf-nvim.setup()*
require("sf-nvim").setup({opts})
        Merge {opts} over the defaults (|sf-nvim-config|), register |:Sf| and,
        if enabled, the default keymaps.

                                                              *sf-nvim.config*
require("sf-nvim").config
        The effective configuration after |sf-nvim.setup()|.

                                                            *sf-nvim.status()*
require("sf-nvim").status()
        Statusline text: the target org alias/username (cached from
        `sf config get target-org` at |sf-nvim.setup()| and updated by
        |:Sf-config-org|), then `⏺ N` while |:Sf-log-tail| is running, where
        N is the number of logs captured. Empty string when nothing is
        known. Example for lualine: >lua

            { function() return require("sf-nvim").status() end }
<
        |User| autocommands `SfTargetChanged` and `SfTailChanged` fire when
        either part changes.

                                                             *sf-nvim.actions*
require("sf-nvim").actions
        Table of `group -> action -> { fn, desc, key }`. This is the source
        for both |:Sf| completion and the default keymaps; call `.fn()` to
        invoke an action directly, e.g. >lua

            require("sf-nvim").actions.test.current.fn()
<
Module functions (all take no arguments unless noted):

    require("sf-nvim.apex")
        .run_test()             tests for the current class
        .run_test_method()      test method under the cursor
        .run_all_tests()
        .execute_script()       current file as anonymous Apex
        .execute_selection({range})
        .find_test_method({lines}, {line}) -> name|nil
        .clear_test_results()

    require("sf-nvim.org")
        .open() .list() .display()
        .create_scratch_org()
        .target                 cached target-org (string|nil)
        .refresh_target({cb}) .set_target({value})
        .find_scratch_defs()    -> { {label, path}, ... }

    require("sf-nvim.project")
        .deploy() .retrieve() .validate()
        .deploy_file({path}) .retrieve_file({path})   default: current buffer
        .set_deploy_on_save({enable})
        .parse_deploy_result({json}) -> qf_items, summary
        .report_deploy({json}, {label}) -> had_failures
        .source_dirs({cwd}) .is_source_file({path}) .source_path_for({path})

    require("sf-nvim.logs")
        .list() .latest() .open({id})
        .tail() .tail_start() .tail_stop() .show()
        .tailing() -> boolean, .tail_count() -> integer
        .debug() .debug_selection({range}) .debug_file({path}, {on_done})
        .parse_run_result({json}) -> SfApexRun|nil
        .render_run({run}) -> lines
        .format_log_item({item}) -> string

    require("sf-nvim.soql")
        .run({query}) .query_buffer() .query_selection({range}) .query_prompt()
        .normalize({lines}) -> string
        .select_fields({query}) -> string[]
        .flatten({record}) -> table<string,string>
        .render({json}, {query}) -> lines

    require("sf-nvim.set-config")
        .set_target_org() .set_target_dev_hub()
        .apply({key}, {org})    `sf config set {key} {org}`, async

    require("sf-nvim.utils.runner")
        .term({argv|cmd}, {opts})           terminal split, opts.on_exit(code); see |sf-nvim-terminal|
        .stream({argv}, {on_line, on_exit}) long-lived process, stdout line by line; :kill() to stop
        .run({argv}, {opts})                async vim.system(); opts.on_exit(code, stdout, stderr)
        .json_async({argv}, {cb}, {opts})   async + JSON decode; cb(data, err)
        .scratch({name, lines, filetype})   read-only result buffer; see |sf-nvim-scratch|

    require("sf-nvim.quickfix")
        .load_from_file({path})             -> boolean (had failures)
        .load_and_open({results_dir})
        .find_latest_test_results({dir})    -> path|nil
        .parse_test_results({json}, {find}) -> items, missing

13. HEALTH CHECK                                              *sf-nvim-health*

`:checkhealth sf-nvim` reports:

- the Neovim version against the supported floor
- whether `sf` and `rg` are on $PATH, and their versions
- whether the current directory contains `sfdx-project.json` and any
  `config/**/*-scratch-def.json` files

It works before |sf-nvim.setup()| has been called.
